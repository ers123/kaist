## 1. 시작하기 전에 (Getting Started)

### Q1. GitHub 계정이 없는데 어떻게 만드나요?

[github.com](https://github.com)에 접속하여 **Sign up** 버튼을 클릭하면 무료로 계정을 만들 수 있습니다. 이메일 주소, 사용자명, 비밀번호만 있으면 됩니다.

- 학교 이메일(`.ac.kr`, `.edu`)로 가입하면 [GitHub Education](https://education.github.com/) 혜택을 받을 수 있습니다 (무제한 Private 리포지토리, Copilot 무료 등).
- 사용자명은 나중에 다른 연구자와 공유할 수 있으므로, 본인 이름이나 연구 관련 이름으로 설정하는 것을 권합니다.
- 2단계 인증(2FA) 설정이 필수입니다. 스마트폰의 인증 앱(Google Authenticator 등)을 사용하세요.

### Q2. Claude Code는 무료인가요? 비용은 얼마나 드나요?

Claude Code는 **유료 서비스**입니다. 두 가지 사용 방식이 있습니다:

| 방식 | 비용 | 특징 |
|------|------|------|
| **Claude Pro 구독** (웹 버전) | 월 $20 | claude.ai에서 GitHub 리포를 연동하여 사용. 일일 사용량 제한 있음 |
| **API 직접 사용** (CLI 버전) | 사용량 기반 과금 | 토큰당 과금. 프로젝트 1건당 $50-200 수준 (데이터 규모에 따라 상이) |

본 프로젝트(15개 기관 인터뷰, 21,011줄)의 경우 전체 분석 과정에서 약 $100-150 수준이 소요되었습니다. 이는 NVivo 같은 상용 질적 분석 소프트웨어의 연간 라이선스($1,000+)에 비해 상당히 경제적입니다.

> **팁**: 처음 시작하는 분에게는 Claude Pro 구독(웹 버전)을 권합니다. CLI 설치 없이 웹 브라우저만으로 사용 가능하고, 월정액이므로 비용 예측이 쉽습니다.

### Q3. 프로그래밍을 전혀 모르는데 사용할 수 있나요?

**네, 사용할 수 있습니다.** 이 워크플로우는 프로그래밍 지식을 요구하지 않습니다.

Claude Code는 자연어(한국어 포함)로 지시하면 알아서 코드를 작성하고 파일을 생성합니다. 연구자가 해야 할 일은:

1. 인터뷰 데이터를 Markdown/CSV 형식으로 준비하기
2. 코드북(분류 기준)을 설계하기
3. Claude Code에게 "이 코드북을 기준으로 인터뷰를 분석해줘"라고 지시하기
4. 결과물을 검토하고 피드백하기

터미널 명령어(`git add`, `git commit` 등)는 몇 가지만 외우면 되며, [GitHub 입문 가이드](howto_github_for_researchers.md)에 모두 설명되어 있습니다. 또한 **GitHub Desktop**(GUI 도구)을 사용하면 터미널 명령어 없이도 가능합니다.

### Q4. 어떤 준비물이 필요한가요?

| 준비물 | 용도 | 필수 여부 |
|--------|------|-----------|
| **GitHub 계정** | 리포지토리 호스팅, 버전 관리 | 필수 |
| **Anthropic 계정** | Claude Code 사용 (claude.ai 또는 API) | 필수 |
| **인터뷰 전사 데이터** | 분석 원본 자료 | 필수 |
| **텍스트 에디터** | 파일 편집, 결과 검토 | 권장 (VS Code 추천) |
| **Gemini 접근** | 코드북 초안 설계 시 긴 컨텍스트 활용 | 선택 |

상세한 설정 방법은 [퀵스타트 가이드 Step 0](howto_quickstart.md)을 참고하세요.

### Q5. Windows/Mac 모두 사용 가능한가요?

**네, Windows, macOS, Linux 모두 지원됩니다.**

- **웹 버전** (claude.ai): 운영체제와 무관하게 웹 브라우저만 있으면 사용 가능합니다. 가장 간편한 방식입니다.
- **CLI 버전**: Node.js(v18 이상)가 설치 가능한 모든 운영체제에서 동작합니다.
  - macOS: Terminal 또는 iTerm2
  - Windows: Windows Terminal 또는 PowerShell
  - Linux: 기본 터미널

> **Windows 사용자 참고**: Git을 설치할 때 [Git for Windows](https://gitforwindows.org/)를 사용하면 Git Bash가 함께 설치되어 편리합니다.

## 2. 데이터 준비 (Data Preparation)

### Q6. 인터뷰 전사본이 HWP/PDF인데 어떻게 변환하나요?

LLM이 가장 잘 처리하는 형식은 **Markdown(.md)**과 **CSV(.csv)**입니다. 형식별 변환 방법은 다음과 같습니다:

| 원본 형식 | 변환 방법 | 비고 |
|-----------|-----------|------|
| **HWP** | 한컴오피스에서 "다른 이름으로 저장" → TXT 또는 DOCX로 저장 → 텍스트 에디터에서 `.md`로 변환 | HWP → DOCX → MD 2단계 변환 필요 |
| **PDF** | (1) 복사/붙여넣기, (2) [Marker](https://github.com/VikParuchuri/marker) 또는 [Docling](https://github.com/DS4SD/docling) 같은 오픈소스 도구 사용 | 스캔된 PDF는 OCR 먼저 필요 |
| **Google Docs** | 파일 → 다운로드 → Markdown(.md) 선택 | 가장 간편 |
| **Word (DOCX)** | (1) 전체 선택 → 텍스트 에디터에 붙여넣기 → `.md`로 저장, (2) [Pandoc](https://pandoc.org/) 사용: `pandoc input.docx -o output.md` | 서식이 복잡하면 Pandoc 권장 |
| **Excel** | 파일 → 다른 이름으로 저장 → CSV UTF-8 (쉼표로 분리) | **반드시 UTF-8 인코딩** 확인 |

변환 후에는 다음을 반드시 확인하세요:
- 한글이 깨지지 않는지 (UTF-8 인코딩 여부)
- 기관별 구분이 명확한지 (`## KAERI`, `## ETRI` 등 제목으로 구분)
- 불필요한 서식(표, 이미지 참조 등)이 제거되었는지

> 자세한 내용은 [퀵스타트 가이드 Step 1](howto_quickstart.md)을 참고하세요.

### Q7. 인터뷰 데이터가 수백 페이지인데 한 번에 처리 가능한가요?

**가능하지만, 전략이 필요합니다.**

본 프로젝트에서는 **21,011줄(약 450,000 단어)**의 인터뷰 데이터를 성공적으로 처리했습니다. 핵심 전략은 다음과 같습니다:

1. **사전 변환 필수**: 원본 데이터를 반드시 Markdown/CSV로 변환한 후 GitHub에 업로드합니다. PDF를 직접 읽히면 세션이 중단될 수 있습니다.
2. **기관별 분할 처리**: 15개 기관 인터뷰를 한 번에 분석하지 않고, "KAERI부터 ETRI까지 먼저 분석해줘"처럼 묶음 단위로 지시합니다.
3. **단계별 분석**: 1차 탐색적 코딩 → 코드북 확정 → 2차 체계적 코딩 → 교차 검증 순서로 진행합니다.

> **주의**: 수백 페이지 PDF를 Claude Code에 직접 읽히면 처리 실패(세션 중단, 응답 없음)가 발생할 수 있습니다. 반드시 텍스트 형식으로 변환한 후 사용하세요.

### Q8. 한국어 데이터도 잘 처리되나요?

**네, Claude는 한국어를 매우 잘 처리합니다.**

본 프로젝트의 인터뷰 전사본은 **전량 한국어**이며, Claude Code가 다음 작업을 성공적으로 수행했습니다:

- 한국어 인터뷰에서 의미 단위(semantic unit) 추출
- 한국어 발화를 영문 코드 체계로 분류
- 한국어 종합 분석 보고서 작성 (`comprehensive_policy_analysis_kor.md`)
- 한국어 ↔ 영어 교차 번역

한 가지 주의할 점은 **코드북의 코드명과 정의를 한국어와 영어 중 어떤 언어로 작성할 것인지** 미리 결정하는 것입니다. 본 프로젝트에서는 코드명을 영어로, 정의 및 예시를 한국어로 병기하여 국제 학술지 투고와 국내 보고서 작성 모두에 활용할 수 있도록 했습니다.

### Q9. 개인정보가 포함된 인터뷰인데 보안은 괜찮나요?

**연구 윤리와 데이터 보안에 대해 반드시 사전 검토가 필요합니다.**

| 고려 사항 | 설명 | 대응 방안 |
|-----------|------|-----------|
| **IRB 심의** | LLM을 통한 인터뷰 데이터 처리는 IRB 심의 대상일 수 있음 | 연구 시작 전 소속 기관 IRB에 LLM 활용 계획을 포함하여 심의 요청 |
| **데이터 전송** | API 사용 시 데이터가 Anthropic 서버로 전송됨 | Anthropic의 [데이터 처리 정책](https://www.anthropic.com/privacy) 확인. API 데이터는 모델 훈련에 사용되지 않음 |
| **GitHub 저장소** | 인터뷰 원본이 저장됨 | **반드시 Private 리포지토리** 사용. 접근 권한을 연구팀에 한정 |
| **비식별화** | 참여자 이름, 직급 등 식별 정보 | 업로드 전 비식별화(가명 처리) 수행 권장 |
| **참여자 동의** | AI 도구 활용에 대한 동의 | 동의서에 "AI 기반 분석 도구 활용" 문구 포함 필요 |

> **핵심**: GitHub Private 리포지토리 + 비식별화 처리 + IRB 승인 세 가지를 반드시 갖추세요. 자세한 내용은 [풀 가이드 2.6절](howto_guide.md)을 참고하세요.

### Q10. CSV 파일은 반드시 만들어야 하나요?

**필수는 아니지만, 강력히 권장합니다.**

Markdown 인터뷰 전사본만으로도 분석은 가능합니다. 그러나 CSV 형식은 다음과 같은 이점이 있습니다:

- **구조화된 검색**: 기관별, 테마별로 필터링하여 특정 발췌문을 빠르게 찾을 수 있습니다.
- **정량 분석 용이**: 빈도 분석, 기관 간 비교 등 정량적 분석이 쉬워집니다.
- **Excel/스프레드시트 호환**: 연구팀 내 비기술 인력도 쉽게 열어볼 수 있습니다.
- **재현 가능성**: 코딩 결과가 행 단위로 정리되어 있어 다른 연구자가 검증하기 쉽습니다.

본 프로젝트에서는 1,527개의 구조화 발췌문을 다음과 같은 CSV 구조로 정리했습니다:

```csv
기관,대분류 테마,중분류 테마,해당 문장 발췌
KAERI,1. 국제협력의 동인 및 목표,기술 확보 및 R&D 역량 강화,"차세대 원자로 개발하는 데 있어서..."
```

> **실전 팁**: 처음부터 CSV를 만들 필요는 없습니다. Markdown 전사본을 먼저 업로드하고, Claude Code에게 "이 인터뷰를 코드북 기준으로 분류하여 CSV로 만들어줘"라고 지시하면 자동 생성됩니다.

## 3. GitHub 사용법 (Using GitHub)

### Q11. Repository를 Private으로 만들면 누가 볼 수 있나요?

Private 리포지토리는 **리포지토리 소유자와 명시적으로 초대받은 사람만** 접근할 수 있습니다.

- 기본적으로 본인만 볼 수 있습니다.
- 공동 연구자를 추가하려면: 리포지토리 → Settings → Collaborators → **Add people**에서 이메일 또는 GitHub 사용자명으로 초대합니다.
- 초대받은 사람도 GitHub 계정이 필요합니다.
- 검색 엔진(Google 등)에 노출되지 않습니다.
- GitHub 직원도 일반적으로 접근하지 않습니다 (법적 요청이 있는 극단적 경우 제외).

> **연구 데이터 보안을 위해 반드시 Private으로 설정하세요.** Public으로 만들면 전 세계 누구나 인터뷰 원본을 열람할 수 있습니다.

### Q12. commit, push, pull이 정확히 뭔가요?

연구 과정에 비유하면 이해가 쉽습니다:

| Git 용어 | 비유 | 설명 |
|----------|------|------|
| **commit** (커밋) | 논문에 "여기까지 저장 + 메모" 남기기 | 파일의 현재 상태를 설명과 함께 저장합니다. `Ctrl+S`와 달리, 이전 상태로 돌아갈 수 있습니다. |
| **push** (푸시) | 저장된 논문을 공용 서버에 올리기 | 내 컴퓨터에 저장된 커밋들을 GitHub 서버로 올립니다. 이후 다른 기기에서도 접근할 수 있습니다. |
| **pull** (풀) | 공용 서버에서 최신 버전 받아오기 | GitHub 서버에 있는 최신 내용을 내 컴퓨터로 가져옵니다. 다른 사람이 수정한 내용을 받아올 때 사용합니다. |

실제 사용 흐름:
```
[내 컴퓨터에서 파일 수정]
    ↓
git add 파일명          ← 변경된 파일을 "저장 대기열"에 올림
    ↓
git commit -m "메시지"  ← 설명과 함께 저장 (commit)
    ↓
git push               ← GitHub 서버로 업로드 (push)
```

> 자세한 설명은 [GitHub 입문 가이드](howto_github_for_researchers.md)의 "핵심 개념 5가지" 섹션을 참고하세요.

### Q13. 브랜치(branch)는 왜 필요한가요?

브랜치는 **원본을 건드리지 않고 별도 공간에서 작업하는 것**입니다.

논문 작성에 비유하면:
- `main` 브랜치 = 검증 완료된 **최종 원고**
- 작업 브랜치 = 최종 원고를 복사해서 만든 **실험적 수정본**

실험적 수정이 마음에 들면 원본에 합치고(merge), 마음에 들지 않으면 복사본만 삭제하면 됩니다. 원본은 항상 안전합니다.

**Claude Code가 자동으로 브랜치를 만드는 이유**: Claude Code에 작업을 지시하면 `claude/analyze-interviews-abc123` 같은 이름의 브랜치를 자동 생성합니다. 이렇게 하면:
- AI가 생성한 결과물이 검증 없이 원본에 반영되는 것을 방지합니다.
- 마음에 들지 않으면 브랜치를 삭제하면 되므로 안전합니다.
- Pull Request를 통해 결과를 검토한 후에만 원본에 반영할 수 있습니다.

### Q14. Pull Request는 꼭 해야 하나요?

**필수는 아니지만, 매우 권장합니다.** 특히 LLM 기반 연구에서는 더욱 중요합니다.

Pull Request(PR)는 **"이 변경 사항을 검토해주세요"라는 요청서**입니다. PR의 장점:

1. **변경 사항 시각화**: "Files changed" 탭에서 무엇이 추가/수정/삭제되었는지 한눈에 확인할 수 있습니다 (빨간색 = 삭제, 초록색 = 추가).
2. **AI 결과 검증**: LLM이 생성한 분석 결과를 연구자가 직접 검토한 후에만 원본에 반영됩니다.
3. **연구 과정 기록**: PR 자체가 "언제, 어떤 분석을, 어떤 검토를 거쳐 반영했는지"의 기록이 됩니다.
4. **협업 편의**: 공동 연구자에게 특정 PR의 URL을 공유하면 해당 변경 사항만 집중적으로 검토할 수 있습니다.

본 프로젝트에서는 총 **9개의 PR**을 통해 분석 과정을 관리했습니다:
```
PR #1  전문가 피드백 생성
PR #3  최종 보고서 (5개 장)
PR #7  종합 정책 분석
PR #9  최종 보고서 개정 + 시각화
...
```

### Q15. 실수로 파일을 잘못 올렸는데 어떻게 되돌리나요?

Git의 가장 큰 장점이 바로 **되돌리기**입니다. 상황별 대처 방법:

| 상황 | 해결 방법 | 명령어 |
|------|-----------|--------|
| 아직 commit하지 않은 수정 되돌리기 | 마지막 commit 상태로 파일 복원 | `git checkout -- 파일명` |
| commit은 했지만 push하지 않은 경우 | 직전 commit 취소 (수정 내용은 유지) | `git reset --soft HEAD~1` |
| 이미 push한 경우 | 되돌리는 새 commit 생성 | `git revert HEAD` |
| 특정 과거 버전의 파일이 필요한 경우 | 해당 시점의 파일만 복원 | `git checkout 커밋ID -- 파일명` |

> **안심 포인트**: Git은 모든 변경 이력을 보관합니다. 실수로 파일을 삭제하거나 덮어써도, 이전 버전으로 언제든 돌아갈 수 있습니다. 이것이 `논문_최종_진짜최종_v2.docx` 같은 파일명 혼란 없이 안전하게 작업할 수 있는 이유입니다.

### Q16. GitHub Desktop을 써도 되나요?

**네, 완전히 사용 가능합니다.** 오히려 터미널이 익숙하지 않다면 GitHub Desktop을 권장합니다.

[GitHub Desktop](https://desktop.github.com/)은 Git의 GUI(그래픽 인터페이스) 도구입니다:

- **commit**: 변경된 파일 목록이 보이고, 체크박스로 선택 → 메시지 입력 → "Commit" 버튼 클릭
- **push**: 상단의 "Push origin" 버튼 클릭
- **pull**: 상단의 "Fetch origin" → "Pull origin" 버튼 클릭
- **브랜치 전환**: 상단 드롭다운 메뉴에서 브랜치 선택

터미널 명령어를 전혀 몰라도 됩니다. 단, Claude Code CLI 버전을 사용할 경우에는 터미널이 필요합니다 (웹 버전은 불필요).

## 4. Claude Code 사용법 (Using Claude Code)

### Q17. Claude Code와 일반 ChatGPT/Claude 웹의 차이는 뭔가요?

핵심 차이는 **파일 시스템 접근 능력**입니다.

| 비교 항목 | 일반 ChatGPT / Claude 웹 | Claude Code |
|-----------|--------------------------|-------------|
| **파일 접근** | 대화창에 붙여넣거나 첨부한 내용만 처리 | GitHub 리포지토리의 **모든 파일**에 직접 접근 |
| **파일 생성/수정** | 코드 블록을 복사/붙여넣기해야 함 | 리포지토리에 **직접 파일 생성/수정** |
| **맥락 유지** | 대화창 내 텍스트만 맥락으로 활용 | 리포지토리 전체 구조와 파일 내용을 맥락으로 활용 |
| **버전 관리** | 없음 | Git commit/push/PR을 자동 생성 |
| **작업 규모** | 한 번에 긴 텍스트 처리 어려움 | 수만 줄 파일도 읽고 분석 가능 |

쉽게 말해, 일반 ChatGPT/Claude는 "대화 상대"이고, Claude Code는 **"연구 프로젝트 전체를 이해하고 직접 작업하는 연구 조교"**입니다. 코드북을 읽고, 인터뷰 전사본을 분석하고, 결과를 파일로 저장하고, Git으로 관리하는 모든 과정을 자율적으로 수행합니다.

### Q18. Claude Code에게 어떻게 지시하면 좋나요? (프롬프트 팁)

효과적인 프롬프트의 핵심은 **구체성**과 **참조 파일 명시**입니다.

**나쁜 예시:**
```
인터뷰 분석해줘.
```

**좋은 예시:**
```
codebook.md의 분류 기준을 사용하여, raw/policy_1027_revised.md에 있는
KAERI, ETRI, KRICT 3개 기관의 인터뷰를 분석해줘.

각 기관별로:
1. 의미 단위(semantic unit)를 추출하고
2. 대분류 테마와 중분류 테마로 분류하고
3. 해당 원문을 발췌하여
4. CSV 형식으로 qualitative/ 폴더에 저장해줘.
```

**프롬프트 작성 팁:**

| 원칙 | 설명 | 예시 |
|------|------|------|
| **참조 파일 명시** | 어떤 파일을 읽어야 하는지 구체적으로 지정 | "codebook.md를 기준으로" |
| **출력 형식 지정** | 결과물의 형태를 명확히 요청 | "CSV 형식으로", "Markdown 표로" |
| **범위 한정** | 한 번에 처리할 범위를 명시 | "KAERI부터 KRICT까지 5개 기관" |
| **단계 분리** | 복잡한 작업은 단계로 나누어 지시 | "먼저 ~하고, 그 다음 ~해줘" |
| **저장 위치 지정** | 결과 파일의 경로를 지정 | "deliverables/ 폴더에 저장해줘" |

### Q19. 분석 도중 세션이 끊기면 어떻게 하나요?

**걱정하지 않아도 됩니다.** Claude Code는 Git 기반으로 작업하므로, 세션이 끊겨도 이미 commit된 내용은 안전하게 보존됩니다.

세션이 끊긴 경우의 대처:

1. **새 세션을 열고 같은 리포지토리에 접속합니다.**
2. **이전 작업 내용을 확인합니다**: Claude Code에게 "지금까지 어떤 파일이 만들어져 있는지 확인해줘"라고 요청합니다.
3. **이어서 작업을 지시합니다**: "KAERI~KRICT는 분석 완료했으니, KIGAM부터 이어서 분석해줘"라고 구체적으로 지시합니다.

> **팁**: 장시간 분석을 진행할 때는 **기관 3-5개 단위로 commit**하도록 지시하세요. "5개 기관 분석이 끝날 때마다 commit해줘"라고 요청하면, 세션이 끊겨도 손실을 최소화할 수 있습니다.

### Q20. Claude Code가 만든 결과가 이상한데 어떻게 수정하나요?

LLM의 결과는 반드시 연구자가 검토해야 합니다. 본 프로젝트에서도 약 **15%의 분류가 수정이 필요했습니다** (정확도 85%).

**수정 방법:**

1. **직접 수정**: 생성된 Markdown/CSV 파일을 텍스트 에디터에서 직접 수정합니다.
2. **Claude Code에 재지시**: "KAERI의 코딩 결과 중 '기술 확보' 범주로 분류된 항목을 다시 검토해줘. 3번과 7번 항목은 '인력 양성'으로 재분류해야 할 것 같아."
3. **코드북 개선 후 재분석**: 특정 범주에서 오류가 반복되면 코드북의 정의를 더 명확하게 수정한 후 해당 부분을 재분석합니다.

> **핵심 원칙**: LLM은 연구자의 **도구(tool)**이지 **대체재(replacement)**가 아닙니다. 최종 판단은 항상 연구자의 몫입니다.

### Q21. 하나의 세션에서 모든 작업을 다 해야 하나요?

**아닙니다.** 오히려 여러 세션에 나누어 작업하는 것이 권장됩니다.

본 프로젝트에서도 약 3주간(2025년 10월 27일 ~ 11월 18일) **9개의 Pull Request**에 걸쳐 작업을 진행했습니다. 각 세션별로 집중할 작업을 나누는 것이 효과적입니다:

| 세션 | 주요 작업 | 소요 시간 |
|------|-----------|-----------|
| 세션 1 | 데이터 변환 및 업로드 | 1-2시간 |
| 세션 2 | 코드북 설계 (Gemini 활용 가능) | 2-4시간 |
| 세션 3-5 | 기관별 체계적 코딩 (5개 기관씩) | 각 2-3시간 |
| 세션 6 | 교차 검증 및 코드북 수정 | 2-3시간 |
| 세션 7 | 종합 분석 보고서 생성 | 3-4시간 |
| 세션 8 | 시각화 및 정책 메모 | 2-3시간 |
| 세션 9 | 최종 검토 및 수정 | 2-3시간 |

Git이 모든 작업 이력을 보존하므로, 세션 간 작업 연속성이 자동으로 유지됩니다.

## 5. 코드북과 코딩 (Codebook & Coding)

### Q22. 코드북은 직접 만들어야 하나요, LLM이 만들어주나요?

**연구자가 설계하고, LLM이 보조합니다.** 코드북 설계는 연구자의 핵심 역할입니다.

권장 워크플로우:

1. **1차 탐색적 분석** (LLM 보조): 인터뷰 전사본을 Claude 또는 Gemini에 투입하여 "이 인터뷰에서 어떤 주제들이 나타나는지 정리해줘"라고 요청합니다. → 초기 테마 도출
2. **코드북 초안 설계** (연구자 주도): 1차 분석 결과를 바탕으로 연구자가 대분류/중분류 코드 체계를 설계합니다. 각 코드에 명확한 정의와 포함/배제 기준을 작성합니다.
3. **파일럿 코딩 및 수정** (반복): 코드북으로 2-3개 기관을 먼저 코딩해보고, 애매한 부분이 발견되면 코드 정의를 수정합니다.
4. **코드북 확정 후 전체 코딩** (LLM 실행): 확정된 코드북을 `codebook.md`로 문서화하고, Claude Code에 전체 분석을 지시합니다.

본 프로젝트의 코드북(`codebook.md`)은 **8대 주제 코드 + 40여 개 세부 코드 + 10개 맥락/뉘앙스 코드**로 구성되었습니다.

> **Gemini 활용 팁**: 코드북 초안 설계 시에는 긴 컨텍스트를 지원하는 Gemini를 활용하면 효과적입니다. 수백 페이지의 인터뷰 전체를 한 번에 투입하여 주제를 탐색할 수 있습니다.

### Q23. 코드북을 수정하면 이전 분석을 다시 해야 하나요?

**이론적으로는 예, 실제로는 부분 재분석이 가능합니다.**

전통적 질적 연구에서는 코드북 수정 후 전체 재코딩에 수주가 소요되었습니다. 하지만 LLM 기반 접근에서는:

- **전체 재분석**: 코드북을 수정하고 "수정된 codebook.md를 기준으로 전체 인터뷰를 다시 코딩해줘"라고 지시하면 수시간 내에 재분석이 완료됩니다.
- **부분 재분석**: 특정 코드만 변경된 경우 "코드 3.2의 정의가 변경되었으니, 기존에 코드 3.2로 분류된 항목만 재검토해줘"와 같이 범위를 한정할 수 있습니다.

본 프로젝트에서도 초기 5대 테마 구조(1차 분석)에서 8대 주제 코드 체계(최종 코드북)로 발전하는 과정에서 반복 분석을 수행했으며, Git 히스토리에 이 과정이 모두 기록되어 있습니다.

> 이것이 LLM 기반 질적 연구의 가장 큰 장점 중 하나인 **반복 가능성(Iterability)**입니다.

### Q24. NVivo 같은 기존 질적 분석 소프트웨어와 병행 가능한가요?

**가능합니다.** 실제로 병행 사용이 유용한 시나리오가 있습니다:

| 병행 방식 | 설명 |
|-----------|------|
| **NVivo로 탐색 → Claude Code로 체계적 코딩** | NVivo에서 소규모 샘플로 탐색적 코딩을 수행하여 코드북을 설계한 후, Claude Code로 대규모 체계적 코딩 수행 |
| **Claude Code로 1차 코딩 → NVivo로 검증** | Claude Code가 생성한 CSV 결과를 NVivo로 가져와서 시각적으로 검토/수정 |
| **교차 검증용** | 동일 데이터를 NVivo(인간 코딩)와 Claude Code(LLM 코딩)로 각각 분석하여 일치도(Cohen's Kappa) 산출 |

CSV 형식은 NVivo와 ATLAS.ti 모두에서 가져오기(import)를 지원하므로, Claude Code의 결과물을 기존 CAQDAS 도구로 원활하게 이전할 수 있습니다.

### Q25. 코딩 결과의 신뢰도는 어떻게 검증하나요?

LLM 기반 코딩의 신뢰도 검증은 **전통적 질적 연구의 신뢰성(trustworthiness) 확보 방법**을 따릅니다:

**1. 교차 검증 (Cross-validation)**
- 전체 데이터의 10-20%를 샘플링하여 연구자가 직접 코딩합니다.
- LLM의 코딩 결과와 연구자의 코딩 결과를 비교하여 **일치도(Cohen's Kappa)**를 산출합니다.
- 본 프로젝트에서는 **85% 일치도**를 달성했으며, 이는 인간 코더 간 신뢰도와 비교해 충분히 경쟁력 있는 수준입니다.

**2. 전문가 검토 (Expert review)**
- 해당 분야 전문가에게 코딩 결과의 일부를 검토 받습니다.
- 본 프로젝트에서는 과학기술정책 전문가의 피드백을 통해 분류의 타당성을 확인했습니다 (`deliverables/llm_analysis_evaluation.md`).

**3. 감사 추적 (Audit trail)**
- Git 히스토리를 통해 코드북의 변천, 분석의 반복 과정, 연구자의 의사결정이 모두 기록됩니다.
- 이는 질적 연구의 투명성(transparency) 확보에 핵심적입니다.

**4. 빈도 기반 검증**
- 코딩 결과의 빈도 분석을 통해 상식적으로 이상한 패턴(과도하게 한 범주에 집중, 특정 기관만 누락 등)이 없는지 확인합니다.

## 6. 분석 결과 및 활용 (Results & Usage)

### Q26. LLM 분석 결과를 논문에 인용해도 되나요?

**가능하지만, 방법론적 투명성이 필요합니다.**

LLM 기반 질적 분석을 학술 논문에 사용할 때 반드시 포함해야 할 사항:

1. **방법론 섹션에 LLM 활용 명시**:
   - 사용한 LLM 모델명과 버전 (예: Claude Sonnet 4.5)
   - 코드북 설계 과정 설명
   - 분류 정확도 / 교차 검증 결과 보고 (예: Cohen's Kappa 0.85)

2. **연구자의 역할 강조**:
   - 코드북 설계, 결과 검증, 해석은 연구자가 수행했음을 명시
   - LLM은 "코딩 보조 도구"로 활용되었음을 서술

3. **재현 가능성 확보**:
   - 코드북을 부록으로 공개
   - GitHub 리포지토리 URL을 제공하여 감사 추적 가능하도록 함

4. **한계점 인정**:
   - LLM 코딩의 정확도 한계 (본 프로젝트: 85%, 즉 15%는 수정 필요)
   - 비언어적 맥락 포착의 한계

> **참고**: 최근 주요 학술지들은 AI 도구 활용을 투명하게 공개하는 조건으로 LLM 기반 분석을 수용하는 추세입니다. 다만, 투고 대상 학술지의 AI 활용 정책을 사전에 확인하세요.

### Q27. 시각화(HTML 파일)를 논문에 넣을 수 있나요?

**HTML 시각화는 직접 논문에 삽입할 수 없지만**, 다음과 같이 활용 가능합니다:

| 활용 방식 | 방법 | 적합한 상황 |
|-----------|------|-------------|
| **스크린샷으로 변환** | 웹 브라우저에서 HTML 열기 → 스크린샷 → 논문에 이미지로 삽입 | 학술지 투고용 |
| **온라인 부록** | GitHub 리포지토리에 HTML 파일 포함 → URL 제공 | 독자가 인터랙티브하게 탐색 가능 |
| **GitHub Pages 배포** | GitHub Pages로 HTML 파일을 웹 호스팅 | 프레젠테이션, 정책 브리핑 등 |
| **정적 이미지로 재생성** | Claude Code에게 "이 시각화를 정적 PNG 이미지로도 만들어줘" 요청 | 인쇄 보고서용 |

본 프로젝트에서 생성된 3종의 인터랙티브 시각화:
- `viz_causal_network.html` — 인과 관계 네트워크
- `viz_heatmap.html` — 기관별 테마 히트맵
- `viz_roadmap.html` — 정책 로드맵

### Q28. 분석 결과물은 어떤 형태로 나오나요?

Claude Code를 통해 생성할 수 있는 결과물의 형태는 다양합니다. 본 프로젝트에서 실제 생성된 산출물을 예로 들면:

| 산출물 유형 | 파일 형식 | 본 프로젝트 예시 | 설명 |
|-------------|-----------|------------------|------|
| **코딩 결과** | CSV, MD | `Policy_merged.csv`, `policy_1027_all_coding.md` | 1,527개 구조화 발췌문 |
| **종합 분석** | MD | `comprehensive_policy_analysis.md` (영문), `_kor.md` (국문) | 기관 간 비교, 패턴 분석 |
| **최종 보고서** | MD | `final_report.md` (4,108줄) | 5개 장 구조의 완전한 보고서 |
| **정책 메모** | MD | `policy_memo.md` | 정책 결정자를 위한 요약본 |
| **인터랙티브 시각화** | HTML | `viz_causal_network.html` 등 3종 | Plotly 기반 인터랙티브 차트 |
| **전문가 피드백** | MD | `feedback.md`, `llm_analysis_evaluation.md` | 분석 품질 평가 |

모든 파일은 **텍스트 기반**(Markdown, CSV, HTML)이므로 Git으로 버전 관리가 가능하고, 어떤 운영체제에서든 열어볼 수 있습니다.

### Q29. 다른 연구 프로젝트에도 동일한 방법을 적용할 수 있나요?

**네, 인터뷰 기반 질적 연구라면 분야와 무관하게 적용 가능합니다.**

이 워크플로우가 적합한 연구 유형:

- 반구조화(semi-structured) 심층 인터뷰 분석
- 포커스 그룹 인터뷰(FGI) 분석
- 개방형 설문 응답 분석
- 정책 문서/보고서 체계적 분석
- 미디어 기사/SNS 텍스트 질적 분석

**적용 시 바꿔야 할 것:**

| 항목 | 본 프로젝트 | 새 프로젝트에서 변경 |
|------|-------------|---------------------|
| 코드북 | 국제협력 관련 8대 테마 | 연구 주제에 맞게 새로 설계 |


## 7. 문제 해결 (Troubleshooting)

### Q30. Git push가 안 됩니다 / 권한 오류가 납니다

**가장 흔한 원인과 해결 방법:**

**원인 1: GitHub 인증이 설정되지 않음**
```bash
# 해결: GitHub CLI로 로그인
gh auth login
# 또는 Personal Access Token(PAT) 설정
```
GitHub은 2021년부터 비밀번호 인증을 중단했습니다. 반드시 **Personal Access Token** 또는 **SSH 키**를 설정해야 합니다.

**원인 2: 리포지토리 접근 권한 없음**
- 다른 사람의 리포지토리에 push하려면 **Collaborator로 초대**받아야 합니다.
- 리포지토리 → Settings → Collaborators에서 확인하세요.

**원인 3: 브랜치 보호 규칙**
- `main` 브랜치에 직접 push가 막혀 있을 수 있습니다.
- 별도 브랜치를 만들어 push한 후 Pull Request로 병합하세요.

**원인 4: 대용량 파일 제한**
- GitHub은 파일 하나당 **100MB** 제한이 있습니다. (Q33 참고)

### Q31. Claude Code가 파일을 읽지 못합니다

**가능한 원인과 해결:**

| 원인 | 증상 | 해결 방법 |
|------|------|-----------|
| **파일 경로 오류** | "파일을 찾을 수 없습니다" | 정확한 파일명과 경로를 확인. 한글 파일명보다 영문 파일명 권장 |
| **파일이 너무 큼** | 응답 없음 / 세션 중단 | 파일을 분할하거나, 특정 범위만 읽도록 지시 ("p.1-100만 읽어줘") |
| **바이너리 파일** | 읽기 실패 | PDF, HWP, DOCX는 먼저 텍스트(MD/CSV)로 변환 필요 |
| **인코딩 문제** | 한글 깨짐 | UTF-8 인코딩으로 재저장. Excel에서 CSV 저장 시 "CSV UTF-8" 선택 |
| **Git에 추가되지 않음** | Claude Code가 인식 못함 | `git add 파일명` → `git commit` → `git push`로 리포에 반영 |

> **팁**: 파일을 읽지 못할 때는 "현재 리포지토리에 어떤 파일이 있는지 목록을 보여줘"라고 먼저 확인해보세요.

### Q32. Markdown 파일이 깨져 보입니다

**인코딩 문제일 가능성이 높습니다.** 해결 방법:

1. **파일 인코딩 확인**: 텍스트 에디터(VS Code 등) 하단 상태바에서 인코딩을 확인합니다. **UTF-8**이어야 합니다.
2. **인코딩 변환**:
   - VS Code: 하단 인코딩 표시 클릭 → "Reopen with Encoding" → UTF-8 선택 → "Save with Encoding" → UTF-8 선택
   - 메모장(Windows): 파일 → 다른 이름으로 저장 → 인코딩을 "UTF-8"로 변경
3. **HWP/Excel 변환 시 주의**: 한컴오피스나 Excel에서 저장할 때 인코딩 옵션이 EUC-KR로 기본 설정되어 있을 수 있습니다. 반드시 **UTF-8**로 저장하세요.

GitHub에서 직접 열어볼 때 정상적으로 보인다면 파일 자체는 정상이며, 로컬 에디터의 인코딩 설정 문제입니다.

### Q33. 대용량 파일 업로드가 안 됩니다

GitHub에는 파일 크기 제한이 있습니다:

| 제한 | 크기 | 설명 |
|------|------|------|
| **단일 파일 경고** | 50MB 이상 | 경고 메시지 표시 |
| **단일 파일 차단** | 100MB 이상 | push 거부됨 |
| **리포지토리 권장** | 1GB 이하 | 전체 리포 크기 |

**해결 방법:**

1. **텍스트 변환**: PDF(수MB~수십MB)를 Markdown(수백KB)으로 변환하면 크기가 대폭 줄어듭니다.
2. **파일 분할**: 하나의 대용량 파일을 여러 개의 작은 파일로 분할합니다. (예: 기관별 별도 파일)
3. **불필요한 파일 제외**: `.gitignore` 파일에 업로드하지 않을 파일 패턴을 지정합니다.
   ```
   # .gitignore 예시
   *.pdf        # 원본 PDF (변환된 MD만 업로드)
   *.hwp        # HWP 파일
   *.mp3        # 인터뷰 녹음 파일
   *.mp4        # 영상 파일
   ```
4. **Git LFS (Large File Storage)**: 100MB 이상의 파일이 반드시 필요한 경우 [Git LFS](https://git-lfs.github.com/)를 사용합니다. 단, 질적 연구에서는 텍스트 변환으로 충분한 경우가 대부분입니다.

> **핵심 원칙**: GitHub에는 **텍스트 파일(MD, CSV, HTML)**만 올리고, 원본 미디어 파일(녹음, 영상, PDF 원본)은 별도 저장소(학교 서버, Google Drive 등)에서 관리하세요.
