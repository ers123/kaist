## Git과 GitHub, 왜 연구에 필요한가?

연구를 하다 보면 이런 파일이 생긴 경험이 있을 겁니다:

```
논문_초고.docx
논문_초고_수정.docx
논문_최종.docx
논문_최종_진짜최종.docx
논문_최종_진짜최종_v2.docx
논문_최종_진짜최종_v2_교수님피드백반영.docx
```

어떤 버전이 가장 최신인지, 무엇이 바뀌었는지 알 수 없게 됩니다. Git은 바로 이 문제를 해결합니다.

- **Git** = 모든 파일의 변경 이력을 자동으로 추적하는 시스템입니다. 어떤 파일이든 "언제, 누가, 무엇을, 왜 바꿨는지" 기록이 남습니다.
- **GitHub** = Git 저장소를 인터넷에 올려두고, 여러 사람이 함께 작업할 수 있게 해주는 서비스입니다.

연구 맥락에서 비유하면:
| 일반적인 파일 관리 | Git/GitHub 기반 관리 |
|---|---|
| `보고서_최종_v3.docx` 같은 파일명 혼란 | 파일은 하나, 변경 이력은 자동 보관 |
| "이 부분 누가 언제 바꿨지?" 추적 불가 | 모든 변경 내역 조회 가능 |
| 이메일로 파일 주고받기 | 온라인에서 변경 사항 확인 및 승인 |
| 실수로 덮어쓰면 복구 어려움 | 이전 상태로 언제든 되돌리기 가능 |

## 핵심 개념 5가지 — 연구자 관점으로 설명

Git/GitHub에는 많은 용어가 있지만, Claude Code를 사용하는 연구자가 반드시 알아야 할 개념은 딱 5가지입니다.

### 1. Repository (리포지토리) = "연구 프로젝트 폴더"

리포지토리(줄여서 "리포" 또는 "repo")는 연구에 필요한 모든 파일과 그 변경 이력을 담는 **온라인 프로젝트 폴더**입니다.

- 하나의 연구 프로젝트 = 하나의 리포지토리로 관리합니다.
- **Private(비공개)**로 만들면 본인과 초대한 사람만 접근할 수 있습니다.
- 이 프로젝트에서는 `raw/`(원본 데이터), `qualitative/`(분석 중간물), `deliverables/`(최종 산출물) 폴더로 구성했습니다.

> 비유: 연구실 공용 서버에 있는 "프로젝트 폴더"와 같지만, 모든 수정 내역이 자동으로 기록되는 폴더입니다.

### 2. Commit (커밋) = "저장 + 메모"

커밋은 파일의 현재 상태를 **설명과 함께 저장**하는 것입니다.

- 논문 작성 시 "초고 완성", "방법론 섹션 수정", "결론 추가"처럼 의미 있는 단위로 중간중간 저장하는 행위와 같습니다.
- 일반 저장(`Ctrl+S`)과의 차이: **이전 상태로 언제든 돌아갈 수 있습니다.**
- 각 커밋에는 "무엇을 왜 바꿨는지" 설명(커밋 메시지)이 붙습니다.

> 비유: Google Docs의 "버전 기록" 기능과 비슷하지만, 연구자가 직접 "이 시점이 중요하다"고 표시하며 메모를 남기는 것입니다.

이 프로젝트의 실제 커밋 메시지 예시:
```
"Add final report Part 3: Chapter 3 - Analysis and Core Findings"
"Add comprehensive expert feedback on science policy interview classification"
```

### 3. Branch (브랜치) = "실험용 복사본"

브랜치는 원본을 건드리지 않고 **별도의 작업 공간**에서 작업하는 것입니다.

- 기본 브랜치인 `main`에는 검증 완료된 최종 결과물이 있습니다.
- 새로운 작업을 할 때는 `main`에서 브랜치를 만들어 그곳에서 작업합니다.
- 작업이 마음에 들면 `main`에 반영하고, 마음에 들지 않으면 버리면 됩니다.

> 비유: 논문 초고를 복사해서 "방법론_실험적수정"이라는 별도 파일을 만드는 것과 같습니다. 원본 초고는 그대로 보존됩니다. 실험적 수정이 잘 되면 원본에 합치고, 아니면 복사본만 삭제하면 됩니다.

**Claude Code가 자동으로 브랜치를 만드는 이유**: 원본(`main`)을 보호하기 위해서입니다. Claude Code에 작업을 지시하면 `claude/analyze-interviews-abc123` 같은 이름의 브랜치를 자동 생성하여 그곳에서 작업합니다.

### 4. Pull Request (PR) = "검토 요청서"

Pull Request(줄여서 "PR")는 **"이 브랜치에서 이런 작업을 했는데, 검토 후 원본에 반영해 주세요"** 라는 요청입니다.

- 브랜치에서 작업한 내용을 `main`에 합치기 전에, 먼저 변경 사항을 보여주고 검토를 요청하는 단계입니다.
- PR의 **"Files changed"** 탭에서 무엇이 추가/수정/삭제되었는지 한눈에 확인할 수 있습니다.

> 비유: 지도교수에게 "이 부분 수정했는데 검토해 주세요"라고 보내는 것과 같습니다. 지도교수가 확인한 후에만 본문에 반영됩니다.

**Claude Code가 PR을 만드는 이유**: 연구자가 결과물을 직접 확인한 후에만 원본(`main`)에 반영되도록 하기 위해서입니다. AI가 생성한 결과를 무조건 수용하는 것이 아니라, 연구자가 **검토하고 승인하는 과정**을 보장합니다.

### 5. Merge (병합) = "승인 후 반영"

Merge는 PR을 검토한 후 **"좋아, 이 변경 사항을 원본에 반영해"** 라고 승인하는 것입니다.

- Merge 버튼을 누르면 브랜치의 변경 사항이 `main`에 합쳐집니다.
- Merge하지 않으면 `main`은 변경되지 않으므로, 안심하고 검토할 수 있습니다.

> 비유: 지도교수가 수정본을 읽어보고 "이 수정 좋네, 본문에 넣어"라고 승인하는 것입니다.

## Claude Code + GitHub: 실제로 일어나는 일

Claude Code 웹 버전에서 작업을 지시하면, 내부적으로 다음 과정이 자동으로 진행됩니다:

```
┌────────────────────────────────────────────────────────────────┐
│  Claude Code + GitHub 워크플로우                                │
├────────────────────────────────────────────────────────────────┤
│                                                                │
│  1단계: 연구자가 Claude Code에 과업 지시                         │
│         "인터뷰 전사록을 코드북 기준으로 코딩해 줘"               │
│              │                                                  │
│              ▼                                                  │
│  2단계: Claude Code가 자동으로 새 브랜치 생성                    │
│         (예: claude/analyze-interviews-abc123)                  │
│              │                                                  │
│              ▼                                                  │
│  3단계: 브랜치에서 파일 생성/수정 + 커밋                         │
│         (main 브랜치는 그대로 보존)                               │
│              │                                                  │
│              ▼                                                  │
│  4단계: 작업 완료 후 Pull Request(PR) 자동 생성                  │
│         "이런 작업을 했습니다. 확인해 주세요"                     │
│              │                                                  │
│              ▼                                                  │
│  5단계: 연구자가 GitHub 웹에서 PR 확인                           │
│         (Files changed 탭에서 변경 내용 검토)                    │
│              │                                                  │
│              ▼                                                  │
│  6단계: 만족하면 Merge → main 브랜치에 반영                      │
│         (수정이 필요하면 Claude Code에 추가 지시)                 │
│                                                                │
└────────────────────────────────────────────────────────────────┘
```

이 프로젝트에서 실제로 만들어진 브랜치 이름의 예시:
```
claude/science-policy-interviews-011CUXesC8zHtKDUA6pmvFVZ
codex/analyze-and-code-interview-transcripts
claude/qualitative-policy-synthesis-016xtsPM6fhmr4SMZ7BSwxNr
```

브랜치 이름이 길고 복잡해 보이지만, 모두 **정상적으로 자동 생성된 것**이니 걱정하지 않으셔도 됩니다. 뒤에 붙는 영문+숫자 코드는 작업 세션을 구분하기 위한 식별자입니다.

## GitHub 웹에서 하는 기본 작업

GitHub는 웹 브라우저에서 모든 작업을 할 수 있습니다. 아래는 연구자가 가장 자주 하게 되는 작업입니다.

### 리포지토리 만들기

1. [github.com](https://github.com)에 로그인합니다.
2. 오른쪽 상단의 **"+"** 버튼 → **"New repository"**를 클릭합니다.
3. Repository name에 프로젝트 이름을 입력합니다 (예: `my-qualitative-research`).
4. **Private**를 선택합니다 (연구 데이터 보호).
5. "Add a README file"에 체크합니다.
6. **"Create repository"** 버튼을 클릭합니다.

### 파일 업로드하기

1. 리포지토리 페이지에서 **"Add file"** → **"Upload files"**를 클릭합니다.
2. 파일을 드래그하거나 선택하여 업로드합니다.
3. 아래쪽 "Commit changes" 영역에 **설명을 작성**합니다 (예: "인터뷰 전사록 15건 업로드").
4. **"Commit changes"** 버튼을 클릭합니다.

> **주의**: 개인 식별 정보가 포함된 원본 데이터는 업로드 전에 반드시 익명화 처리하세요.

### Pull Request 확인하고 Merge하기

Claude Code가 작업을 완료하면 PR이 생성됩니다. 이를 확인하고 반영하는 방법:

1. 리포지토리 페이지 상단의 **"Pull requests"** 탭을 클릭합니다.
2. 열려 있는 PR을 클릭하여 엽니다.
3. **"Files changed"** 탭에서 변경된 내용을 확인합니다.
   - 초록색 배경 = 새로 추가된 내용
   - 빨간색 배경 = 삭제된 내용
4. 내용이 만족스러우면 **"Merge pull request"** → **"Confirm merge"**를 클릭합니다.
5. 이제 변경 사항이 `main` 브랜치에 반영되었습니다.

### 파일 변경 이력 보기

특정 파일이 어떻게 변해왔는지 확인하고 싶을 때:

1. 리포지토리에서 해당 파일을 클릭합니다.
2. 파일 상단의 **"History"** 버튼을 클릭합니다.
3. 각 커밋을 클릭하면 그 시점에서 무엇이 변경되었는지 확인할 수 있습니다.

## 자주 묻는 질문 (FAQ)

**Q: 브랜치가 여러 개 생겼는데, 내 최종 파일은 어디에 있나요?**
A: **`main` 브랜치**에 있습니다. PR을 Merge했다면 해당 변경 사항이 `main`에 반영된 것입니다. 리포지토리 페이지 왼쪽 상단의 브랜치 선택 메뉴에서 `main`이 선택되어 있는지 확인하세요.

**Q: PR을 Merge하지 않으면 어떻게 되나요?**
A: `main` 브랜치는 전혀 변경되지 않습니다. 브랜치에서 작업한 내용은 그대로 보존되어 있으므로, 나중에 다시 검토하고 Merge할 수 있습니다. 불필요하다고 판단되면 PR을 닫아도(Close) 됩니다.

**Q: 실수로 잘못된 파일을 올렸어요. 되돌릴 수 있나요?**
A: 네, Git은 모든 변경 이력을 보관하므로 이전 상태로 돌아갈 수 있습니다. 간단한 경우 GitHub 웹에서 해당 파일의 이전 버전을 확인하고 복원할 수 있습니다. 복잡한 경우 Claude Code에 "이전 상태로 되돌려 줘"라고 지시할 수 있습니다.

**Q: Private 리포지토리의 데이터를 다른 사람이 볼 수 있나요?**
A: 본인이 명시적으로 접근 권한(Collaborator)을 부여하지 않는 한 **아무도 볼 수 없습니다**. Settings → Collaborators에서 초대한 사람만 접근 가능합니다.

**Q: Claude Code가 만든 브랜치 이름이 이상해요 (`claude/blah-blah-abc123`). 정상인가요?**
A: 정상입니다. `claude/` 또는 `codex/`로 시작하는 브랜치 이름은 AI 에이전트가 자동 생성한 것입니다. 뒤쪽의 영문+숫자 코드는 작업 세션 식별자로, 같은 작업을 여러 번 할 때 구분하기 위해 자동으로 붙습니다.

**Q: Merge 후에 브랜치를 삭제해도 되나요?**
A: 네, Merge가 완료되면 해당 브랜치는 더 이상 필요하지 않습니다. GitHub에서 Merge 직후 "Delete branch" 버튼이 나타나는데, 클릭하여 정리해도 됩니다. 변경 이력은 `main`에 모두 보존되어 있습니다.

**Q: 여러 명이 동시에 작업할 수 있나요?**
A: 네, 각자 다른 브랜치에서 작업하면 서로의 작업에 영향을 주지 않습니다. 각 작업이 완료되면 별도의 PR을 통해 `main`에 순차적으로 반영하면 됩니다.

## 용어 사전 (빠른 참조)

| 용어 | 한국어 설명 | 연구 비유 |
|------|-----------|----------|
| **Repository (리포)** | 프로젝트의 모든 파일과 변경 이력을 담는 저장소 | 연구 프로젝트 폴더 (버전 기록 포함) |
| **Commit (커밋)** | 변경 사항을 설명과 함께 저장하는 행위 | "초고 완성", "방법론 수정" 같은 중간 저장 |
| **Branch (브랜치)** | 원본에 영향을 주지 않는 독립적 작업 공간 | 논문 초고의 "실험적 수정" 복사본 |
| **Main (메인)** | 검증 완료된 최종 결과물이 있는 기본 브랜치 | 최종 승인된 논문 본문 |
| **Pull Request (PR)** | 브랜치의 변경 사항을 검토 요청하는 절차 | 지도교수에게 "검토해 주세요" 보내기 |
| **Merge (병합)** | PR 승인 후 변경 사항을 main에 반영하는 행위 | 지도교수의 "이 수정 반영해" 승인 |
| **Clone (클론)** | 원격 저장소를 내 컴퓨터에 복사하는 것 | 공용 서버의 프로젝트 폴더를 내 PC에 복사 |
| **Push (푸시)** | 내 컴퓨터의 변경 사항을 원격 저장소에 올리는 것 | 수정한 파일을 공용 서버에 업로드 |
| **Pull (풀)** | 원격 저장소의 최신 변경 사항을 내 컴퓨터에 받는 것 | 공용 서버의 최신 파일을 내 PC에 다운로드 |
| **Diff (디프)** | 두 버전 간의 차이점을 보여주는 것 | Word의 "변경 내용 추적"과 유사 |
| **Files changed** | PR에서 변경된 파일 목록과 내용을 보여주는 탭 | 수정 전후 비교표 |
| **.gitignore** | Git이 추적하지 않을 파일을 지정하는 설정 파일 | "이 파일은 서버에 올리지 마세요" 목록 |
| **Collaborator** | 리포지토리에 접근 권한을 부여받은 사람 | 공동 연구자, 지도교수 |
